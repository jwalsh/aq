* 0. The Core Problem

Every transport can:
- Return =True= then fail on =send()=
- Hang indefinitely on =send()= after reporting available
- Accept the write, return =True=, and silently drop it
- Deliver to self but not to peers (split MQTT broker)
- Deliver with arbitrary delay (LoRa queue backed up, git pending merge)

=is_available()= is a point-in-time snapshot of a system that changes
between the check and the use. This is TOCTOU at the transport layer.

* 2. SendResult: Three Outcomes, Not Two

#+begin_src python
class SendResult(Enum):
    CONFIRMED   # peer acknowledged
    ACCEPTED    # transport accepted, delivery unknown
    FAILED      # transport rejected
    TIMEOUT     # no response within deadline
#+end_src

Convergent multicast only works if you know which leg actually
delivered. Otherwise you cannot distinguish "mesh delivered, MQTT
redundant" from "both dropped silently."

Current =mesh.py= returns =bool=. That conflates ACCEPTED with
CONFIRMED. The transport protocol interface needs this enum.

* 3. Sequence Number Fragility

=(agent, seq)= dedup assumes seq numbers are reliable. Under chaos:

| Failure | Effect | Looks like |
|---------+--------+------------|
| seq gap | transport dropped msg | message loss or "not yet delivered" |
| seq reorder | multi-hop LoRa delivers 3 before 2 | corruption |
| seq reuse | agent reboots, counter resets to 0 | replay attack |
| seq stale | old message arrives after new one | phantom |

** 3.1 The Godot problem

Voltage drops to 10% -> sends alert -> reboots -> seq resets to 0 ->
peers see seq 0 again. Is this a new session or replay?

The alert that triggered the reboot is now ambiguous.

Fix: session ID (boot count or timestamp) prepended to seq. Requires
persistent storage across reboots -- which a voltage-depleted node
may not complete. The fix itself has a failure mode.

** 3.2 Gap detection

"If I haven't seen seq N+1 within =2*Imax=, declare N the last."

This is a tombstone TTL. It conflates "slow transport" with "dead
agent." A message delayed by 3*Imax (git push pending merge conflict)
arrives after the tombstone and is treated as a ghost.

** 3.3 What production systems do

- Cassandra: vector clocks + hinted handoff + read repair
- Consul: Serf protocol with separate ack path
- Raft: leader confirms commit to majority before acknowledging

All have an acknowledgment path because "I wrote it to the network"
and "the peer received it" are different events separated by physics.

* 7. The Structural Fix for aq v0.5

The transport protocol interface needs:

#+begin_src python
class Transport(Protocol):
    def send(self, broadcast: Broadcast) -> SendResult: ...
    def receive(self, channel: str) -> list[Broadcast]: ...
    def is_available(self) -> bool: ...      # advisory, may lie
    def confirm(self, msg_id: str) -> bool:  # peer ACK check
        return False  # default: no confirmation path
#+end_src

=confirm()= is optional. Filesystem has none (write = done). MQTT
could use retained message or /ack topic. LoRa has none (fire and
forget). Git has none (push succeeds ≠ peer pulled). GH Issues could
check for reaction emoji.

For transports without confirmation, AMTP SYNC messages serve as
application-level ACK: "I've seen your messages up to seq N." This
is scuttlebutt anti-entropy. The transport doesn't need to confirm
if the protocol layer can detect gaps.

* 8. The Honest Summary

The current convergent multicast plan assumes transports fail cleanly.
They won't. The interesting failure is ACCEPTED with silent drop --
the transport that lies.

Every production gossip system (Cassandra, Consul, Serf) has an
acknowledgment path specifically because "I wrote it to the network"
and "the peer received it" are different events separated by physics.

AMTP's SYNC messages are the ack path. But SYNC itself travels over
the same unreliable transports. Turtles all the way down. At some
point you accept that gossip is best-effort and the failure mode is
"message arrives late or not at all" which is... the design.
