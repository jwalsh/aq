  roadmap. It characterizes the March 2026 industry state in agentic
  observability (IBM, Microsoft, Azure, Grafana, and the OTel ecosystem),
  contrasts the dominant command-and-control model against ~aq~'s gossip
  architecture, and surfaces conjectures for the transport registry and
  monitoring layer.

  Agents consuming this document should treat it as a terministic screen
  (Burke): the vocabulary chosen here shapes which problems are visible.
  The industry uses "observability," "tracing," "telemetry." ~aq~ uses
  "presence," "gossip," "TTL." These are not synonyms. The distinction
  is load-bearing.

** Architecture
   ~aq~ sits at L1.5 of the Seven Concerns agentic stack — between L1
   (Work / ~bd~ beads, authoritative state) and L2 (Memory / ~JITIR~,
   retrieval). Its purpose is ambient presence broadcast: not "what is
   true" but "what is currently being attempted, by whom, where."

** Dominant Model: Command-and-Control + OTel Traces

   The industry has converged on a single architecture for agentic
   monitoring in Q1 2026:

   The model requires: (1) SDK instrumentation of every agent, (2)
   a collector process, (3) a persistent backend, (4) a query layer.
   All four must be operational before a single presence signal is visible.

** IBM (March 2026)

   IBM's 2026 observability framing centers on agents ingesting MELT
   telemetry (metrics, events, logs, traces) to remediate issues
   autonomously — agents consuming observability rather than producing
   gossip. IBM BeeAI, LangChain, LangGraph, and AutoGen are cited as
   the common SDK layer. Token usage, tool interactions, and agent
   decision paths are the new signals added to standard MELT.

   IBM Consulting Advantage (ICA), announced January 19 2026 on Azure,
   adds an A2A gateway and MCP server management layer — structured
   command-and-control over agent coordination. Observability and
   traceability are listed as features of the coordination layer, not
   a separate concern.

   *Relevance to aq:* IBM BeeAI is open-source; could emit aq-style
   NDJSON gossip payloads as a side-channel alongside OTel traces.
   A2A is structurally equivalent to SOAP/WS-* (see ~TRANSPORTS.org~);
   ~aq~ sits below this layer and does not compete with it.

** Microsoft / Azure (February–March 2026)

   Microsoft's security blog (March 18 2026) frames AI observability
   as a security requirement: traditional health metrics stay green
   during agent compromise. Their example — a research agent poisoned
   by hidden page instructions passing bad context to an email agent —
   illustrates a failure mode that OTel traces would catch post-hoc
   but ~aq~ presence broadcast would not prevent.

   Azure Copilot's observability agent (announced at Ignite, live Feb 2026)
   provides full-stack visibility with every agent action reviewable,
   traceable, and auditable. Governance is the primary design goal;
   autonomy is constrained by RBAC at every layer.

   *Relevance to aq:* Azure's model is the opposite of ~aq~. Where Azure
   requires every action to honor policy and remain auditable, ~aq~ is
   lossy-ok and TTL-bounded by design. The threat model is different:
   Azure guards against agent compromise; ~aq~ guards against merge
   conflicts and work duplication. These are complementary failure modes,
   not competing ones.

** Grafana MQTT Datasource (March 2 2026)

   Grafana's official ~grafana-mqtt-datasource~ plugin shipped v1.3.1
   on March 2 2026 (Go 1.26, CVE fix). It connects directly to a
   Mosquitto broker and streams topic messages into dashboard panels
   in real time — no Telegraf intermediary required for live view.

   Constraints relevant to ~aq~:
   - Live data only; no historical queries. Panels show data received
     while open. Historical path requires InfluxDB.
   - All subscriptions use QoS 0 only. Claim events (QoS 1 in ~aq~
     transport spec) require the Telegraf → InfluxDB path for durability.
   - MQTT v3.1.x only; no v5.
   - Provisioning-as-code supported via YAML datasource config and
     Terraform provider.

   Install path for the broker host:
#+begin_src sh :tangle deploy/install-grafana-mqtt.sh
#!/bin/sh
# Install Grafana MQTT datasource on the broker host
grafana-cli plugins install grafana-mqtt-datasource
service grafana restart
#+end_src

   Provisioning config:
#+begin_src yaml :tangle deploy/grafana-provisioning/datasources/mqtt-agents.yaml
apiVersion: 1
datasources:
  - name: MQTT-agents
    type: grafana-mqtt-datasource
    jsonData:
      uri: tcp://localhost:1883
      clientID: grafana-aq
    isDefault: false
#+end_src

** OTel Ecosystem: AgentOps, Langfuse, Arize, Maxim

   The emerging platform layer (benchmarked January 2026 against 100
   identical queries through a multi-agent travel planning system):

   | Platform  | Overhead | Approach               | SDK required? |
   |-----------+----------+------------------------+---------------|
   | Laminar   | ~5%      | lightweight tracing    | yes           |
   | LangSmith | ~8%      | LangChain-native       | yes           |
   | AgentOps  | ~12%     | decoupled integration  | yes           |
   | Langfuse  | ~15%     | step-level depth       | yes           |

   All require SDK instrumentation. None support a gossip/presence
   model. None address the bootstrap paradox (the agent must be
   running and instrumented before it can report it is running).

* Contrast: Gossip vs. Trace

#+begin_src mermaid :tangle docs/gossip-vs-trace.mmd
graph TD
  subgraph "Industry (OTel/Trace)"

    SDK1 -->|push| COL[Collector]
    COL -->|store| BACK[Backend]
    BACK -->|query| DASH[Dashboard]

  end

  subgraph "aq (Gossip/Presence)"
    direction LR
    A2[Agent] -->|broadcast NDJSON| FILE[AQ_HOME file / MQTT topic]
    FILE -->|subscribe| ANY[Any listener]
    NOTE2[Requires: write access to AQ_HOME\nFirst signal on first write\nNo coordinator, no SDK]
  end

  style NOTE1 fill:#fdd
  style NOTE2 fill:#dfd
#+end_src

  | Dimension          | Industry OTel model         | aq gossip model              |
  |--------------------+-----------------------------+------------------------------|
  | Bootstrap          | collector must be running   | no bootstrap required        |
  | Agent cooperation  | SDK instrumentation needed  | write to AQ_HOME only        |
  | Delivery guarantee | at-least-once (OTel gRPC)   | lossy-ok, QoS 0 default      |
  | Historical data    | stored in backend           | TTL-bounded, ephemeral       |
  | Conflict detection | post-hoc trace correlation  | real-time presence broadcast |
  | Failure mode       | silent on compromise        | silent on partition          |
  | Governance model   | RBAC + audit log            | none (by design)             |
  | Overhead           | 5–15% per benchmark         | near-zero (file write / pub) |

  The gossip model trades auditability and governance for speed and
  zero-coordination bootstrapping. This is the correct trade-off at L1.5.
  Governance belongs at L5 (SEFACA). Audit logs belong at L6 (pitcrew).
  Presence broadcast does not need to carry that weight.
